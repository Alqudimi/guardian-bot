# خطة تطوير Guardian Bot

## الهدف
رفع جودة وأمان وقابلية توسع بوت Telegram مع الحفاظ على معماريته ذات الطبقات، وإصلاح الأعطال المثبتة، وتقوية حدود التشغيل، ثم إضافة اختبارات فعلية قابلة لإعادة الإنتاج وتوثيق النتائج.

## نتائج الاستطلاع الأولي

المشروع Python 3.11+ ويستخدم `python-telegram-bot` وPydantic Settings وSQLAlchemy async وRedis وCelery ونماذج Transformers اختيارية. يوجد 118 ملف Python تقريباً و10 ملفات اختبارات وحوالي 17 ألف سطر في `src/` و`config/`. نقطة الدخول هي `main.py`، ومسار الإشراف الرئيسي يمر عبر `src/handlers/message_handler.py` ثم `src/pipeline/orchestrator.py` ثم طبقات التحليل والقرار والتنفيذ والتدقيق.

المعمارية الفعلية أوسع من وصف README؛ المنسق يعلن 17 طبقة ويشغّل مجموعات من الطبقات بالتوازي، كما توجد ميزات الألعاب والمتجر والإدارة في نفس تطبيق Telegram. أكبر بؤر التعقيد هي `message_handler.py` و`admin_commands.py` و`action_execution.py`، وهي تحتاج ضبط حدود المسؤوليات قبل التوسع.

خط الأساس بعد تثبيت الاعتماديات الخفيفة: **119 اختباراً ناجحاً و36 اختباراً فاشلاً**. جميع الإخفاقات الحالية مرتبطة بتهيئة `telegram_admin_ids`: عندما يصل معرف واحد كقيمة عددية، يحاول validator تحويل العدد إلى iterable، فينتج `TypeError: 'int' object is not iterable`. هذا عطل حقيقي يمنع كثيراً من الوحدات من الإقلاع أو الاختبار.

## القرارات المعمارية

1. الحفاظ على المنسق ذي الطبقات وعدم إعادة كتابة النظام إلى إطار مختلف.
2. إبقاء منطق المجال مستقلاً قدر الإمكان عن Telegram وRedis، مع إدخال حدود صغيرة واضحة عند الحاجة.
3. جعل إعدادات الإنتاج fail-closed: لا قيمة افتراضية قابلة للاستخدام لتوكن البوت، والتحقق من URL والـ secret وقيود المعدلات.
4. منع الإجراءات الأمنية غير الذرية في Redis؛ يجب أن تكون حصص المعدل والتبريد والحدود قابلة للتسابق بأقل قدر ممكن باستخدام Lua أو عمليات ذرية.
5. عدم تشغيل نماذج AI في الاختبارات العادية، مع اختبار مسارات degraded mode وقيود الموارد بصورة حقيقية محلياً.
6. عدم تنفيذ أفعال Telegram المدمرة فعلياً من بيئة التطوير لغياب اعتماد المستخدم على مجموعة اختبار؛ بدلاً من ذلك تُختبر الحدود الداخلية مع Bot API عبر اختبار تكاملي غير مدمر، وتوثّق الحاجة إلى مجموعة اختبار يملكها المستخدم لأي اختبار حي.

## معايير القبول

يُعد العمل منجزاً عندما تمر الاختبارات الحالية والجديدة، وتفشل الإعدادات غير الآمنة بوضوح قبل بدء البوت، ولا توجد مسارات إدارة تعتمد على هوية غير موثوقة، ولا تُسجّل الأسرار، وتبقى طبقات الحماية قابلة للتعطيل الجزئي عند فشل خدمة اختيارية، وتكون خطوات التشغيل والاختبار قابلة لإعادة الإنتاج.

## المخاطر والقيود

| الخطر أو القيد | الأثر | المعالجة |
|---|---|---|
| لا يوجد token أو مجموعة Telegram اختبار مقدمة | لا يمكن تنفيذ حذف/حظر حي بأمان | اختبارات غير مدمرة محلية، وتوثيق اختبار حي اختياري يحتاج اعتماد المستخدم |
| احتمال غياب Redis/PostgreSQL/Docker في البيئة | تعذر اختبارات التكامل | فحص توفر الخدمات، وتشغيل الاختبارات الممكنة، وإظهار الفشل صراحة |
| نماذج AI كبيرة | بطء واستهلاك ذاكرة | اختبارات degraded mode وحدود مهلة، وعدم تنزيل النماذج في دورة الاختبارات العادية |
| تداخل الألعاب والمتجر والإشراف | سباقات أو تغيير سلوك المستخدم | اختبار ترتيب handlers وفصل مسؤوليات التسجيل قبل أي توسع |
| ملفات كبيرة وتعديلات واسعة | صعوبة المراجعة | شرائح صغيرة، تحقق بعد كل مجموعة، وعدم الإفراط في تحسين مكون مكتمل |
